# Backend Audit — Highlights, Explanations, Canvas, Auth

Scope: `apps/api/papertree_api/{highlights,explanations,canvas,auth}/*`, `database.py`.
Cross-referenced against the frontend callers that actually produce the stored data
(`apps/web/src/lib/api.ts`, `apps/web/src/app/paper/[id]/read/page.tsx`,
`apps/web/src/components/reader/{PDFViewer,BookViewer}.tsx`) because the backend accepts
untyped dicts and cannot be understood without knowing what the client puts in them.

---

## What this subsystem actually does

**Highlights.** There are two parallel, incompatible highlight APIs living in one router.
The "legacy" one (`POST /highlights/`, `GET /highlights/book/{id}`, `PATCH`, `DELETE`,
`/explain`, `/search`, `/export`) is keyed on `book_id`, stores a `position` object, and
writes explanations into `db.highlight_explanations`. The "new" one
(`GET|POST /highlights/papers/{paper_id}`) is keyed on `paper_id`, stores `rects`/`anchor`/
`section_id`, and its delete cleans up `db.explanations`. Every legacy route is dead code at
runtime — they all do `str(user["_id"])` while `get_current_user` returns `{"id", "email"}`
(`auth/utils.py:92`), so they raise `KeyError: '_id'` → HTTP 500. The frontend still calls
one of them for deletion.

The anchor that is actually persisted is: `page_number` (int), `section_id` (string like
`page-3`), `selected_text`, and `rects` — an untyped `List[dict]` of window-normalised
**viewport** coordinates. No PDF user-space coordinates, no page dimensions, no character
offsets, no block id. `TextAnchor` (exact/prefix/suffix/section_path) is modelled at
`highlights/models.py:78` and is never populated by any client.

**Explanations.** `POST /explanations/papers/{paper_id}` takes a `highlight_id` + question,
finds the highlight's text inside the paper's flat `extracted_text` blob by naive substring
search, grabs ±500 characters, calls OpenRouter synchronously inside the request, and stores
`{question, answer_markdown, model, ask_mode, parent_id}`. `parent_id` gives a tree, rebuilt
by unbounded recursion in `build_thread`. The `auto_add_to_canvas` flag (default `true`) is
inert — it imports two symbols that do not exist anywhere in the repo.

**Canvas.** A canvas is one Mongo document per (paper, user) with an embedded
`elements.{nodes,edges}` array. A "node" is a plain dict with `id`, `type`, `position{x,y}`,
`data{...}`, `parent_id`, `children_ids`. There is no node collection — `db.canvas_nodes` is
indexed but never written or read. Nodes are generated by `explore` (highlight → excerpt node
→ AI node), `ask` (follow-up), `note`, `expand-page`, and `populate`, which mass-generates one
node per PDF page plus one per highlight plus one per explanation.

**Auth.** Email + bcrypt(12) + HS256 JWT, 7-day expiry, no refresh, no revocation, no `jti`,
default secret baked into `config.py:14`. `get_current_user` re-reads the user on every
request and returns `{"id", "email"}`.

## Data flow

```
PDF upload → fitz page.get_text("text") joined with "[Page N]" markers → papers.extracted_text (flat blob)
          → LLM → papers.book_content.page_summaries  (AI-generated prose)

Reader (PDF mode)  → range.getClientRects() [viewport px, scroll-dependent]
                   → /window.innerWidth,/window.innerHeight  → rects
                   → POST /highlights/papers/{id}          → highlights doc
Reader (Book mode) → selection over AI page summary text   → {selected_text, section_id, page_number}
                   → POST /highlights/papers/{id}          → highlights doc (indistinguishable from PDF-mode)

Highlight → POST /explanations/papers/{id} → substring-search extracted_text → OpenRouter (sync, 90s)
          → explanations doc {question, answer_markdown, model} ; canvas link silently fails

Canvas    → get_or_create_canvas → whole-document $set on every node move / add / delete
          → populate_canvas rewrites the entire nodes+edges array in one update
```

Everything is synchronous. There is no job queue, no streaming, no idempotency key on the new
explanation path, and no optimistic-concurrency token on canvas writes — the last PUT wins and
silently discards concurrent edits.

### Mongo indexes vs. actual queries (`database.py`)

Indexed but never queried: `db.canvas_nodes` (three indexes, `:37-39`) — the collection does
not exist, canvas nodes are embedded. `db.paper_images` (`:19`) — no code touches it.
`db.canvases` `(user_id, book_id)` (`:36`) — canvases have no `book_id`.
`db.highlights` `(section_id)` (`:21`) — `section_id` is written and returned but never used
in a filter. `db.explanations` `(canvas_node_id)` (`:25`) — the field is only ever set to
`None` because the auto-canvas import fails.

Queried but unindexed: `db.highlight_explanations` by `{highlight_id, user_id}`
(`highlights/routes.py:216`) — only `(highlight_id, mode)` is indexed. `db.explanations` by
`{paper_id, user_id}` (`explanations/routes.py:187`, `canvas/services.py:281`) — the compound
index is `(paper_id, highlight_id)`, so `user_id` is not covered. `db.highlights` by
`{user_id, $or:[{paper_id},{book_id}]}` (`highlights/routes.py:325`) — served by two
different indexes with different key orders, no single covering index. `db.papers` by `_id`
alone is fine, but no `(_id, user_id)` composite exists for the very common ownership check.

Index creation also runs unconditionally on every startup inside `connect_to_mongo`, including
a text index build, blocking the lifespan handler.

## What is worth keeping

- **`auth/utils.py` password handling.** bcrypt with `gensalt(rounds=12)`, constant-time
  `checkpw`, exception-safe verify. This is correct and should survive untouched.
- **The `AskMode` prompt taxonomy** (`explanations/services.py:11-50`). Six well-differentiated
  modes with sane formatting contracts. Worth keeping as data (versioned prompt records),
  not as a module-level dict.
- **`ExplanationCreate.parent_id`** — the tree shape is the right primitive for branched
  reading; only the traversal and ownership enforcement are wrong.
- **`papers/extraction.py` (1016 lines, never imported by anything).** It already defines
  `ContentBlock` with a `SourceLocation`, `BoundingBox`, per-block ids, `OutlineItem.block_id`,
  math-font detection and `ExtractedImage.bbox` (`:210-248`). This is precisely the
  document-coordinate provenance model the rest of the codebase lacks, and it is dead code
  while `papers/routes.py:25-37` uses a five-line flat-text extractor instead. Adopting it is
  the single highest-leverage change available.
- **`CanvasElements`/`CanvasNode` Pydantic models** (`canvas/models.py:92-104`) — a reasonable
  node schema that the routes bypass entirely in favour of raw dicts. Enforce them.
- **Idempotency-by-lookup in the legacy explain path** (`highlights/routes.py:154-161`) and its
  token/cost recording (`:189-194`) — the newer path lost both.

## What should go

- The entire legacy highlight surface: `HighlightCreate`, `HighlightPosition`, `HighlightInDB`,
  `HighlightUpdate`, `HighlightSearchQuery`, `HighlightExplanation*` and routes
  `highlights/routes.py:17-311`. It cannot execute (`user["_id"]`), targets a non-existent
  `db.books`, and duplicates the paper-based API.
- `services/ai.py` in full — a second OpenRouter client with its own model table, its own
  prompt set, its own cost estimator and a leaky global cache, reachable only from dead routes.
  One LLM client (`explanations/services.py`) should exist.
- `db.canvas_nodes`, `db.paper_images`, `db.books`, `db.highlight_explanations` and their
  indexes. Also `PyObjectId` (`highlights/models.py:10`, unused), `BatchExportRequest/Response`
  (`canvas/models.py:157-166`, no route implements them — and `read/page.tsx:296` calls
  `canvasApi.batchExport`, which is not defined in `api.ts`, so the Export-to-Canvas button
  throws a TypeError).
- The `auto_add_to_canvas` block (`explanations/routes.py:127-158`) — delete it or implement
  it; a default-true flag that has never once executed is worse than no flag.
- Every dual-write "backward compat" field: `book_id` mirroring `paper_id`, `text` mirroring
  `selected_text`, and the synthesised `position` (`highlights/routes.py:369-387`). They double
  the write, halve the index utility, and guarantee the two copies drift.
- The `rects` field as currently specified. Whatever replaces it must be typed, must name its
  coordinate space, and must carry the page's PDF-space dimensions.
- `_tree_layout` exists twice with different behaviour (`canvas/routes.py:207` and
  `canvas/services.py:25`); the routes copy is the weaker one and the routes module imports
  neither consistently.

## Open questions

1. **Is "Book mode" meant to be the paper or a summary of the paper?** Today it renders
   `page_summaries` (LLM output) and lets users highlight it, storing the result as a highlight
   of page N. If Book mode is meant to be reflowed *source* text, the whole book pipeline needs
   rebuilding on extracted blocks; if it is meant to be a summary, highlights over it need a
   different type and must never be fed back to the model as paper text.
2. **What is the intended anchor primitive?** Nothing in the codebase commits to one. The
   product vision (stable annotation across zoom, resize, reflow, re-parse) needs at minimum
   `{page, pdf_space_bbox[], block_id, char_range}` plus a text-quote fallback. `TextAnchor`
   was designed for this and abandoned.
3. **Does any production data exist?** If yes, every stored `rects` array is unrecoverable and
   a migration can only re-anchor by fuzzy-matching `selected_text` against re-extracted blocks
   — which will fail wherever the same string occurs twice on a page.
4. **Should the canvas be a document or a graph?** A single embedded document cannot support
   the auto-populated 60+-node graphs `populate_canvas` creates, nor multi-device editing.
5. **Where does long-running LLM work belong?** Every generation currently blocks a request for
   up to 90 s with no queue, no retry, no per-user quota and no cancellation.
6. **Is `db.highlight_explanations` populated in any existing deployment?** It determines
   whether the collection can simply be dropped or needs a merge into `db.explanations`.
