# Audit — Frontend: Reader

Scope: `apps/web/src/app/paper/[id]/read/page.tsx`, all of `apps/web/src/components/reader/*`, `apps/web/src/store/readerStore.ts`, `apps/web/src/store/highlightStore.ts`. Backend files read only to establish provenance of `smart_outline` and `book_content`.

---

## What this subsystem actually does

**It is two unrelated readers bolted to one toolbar.**

`settings.mode === 'pdf'` renders `PDFViewer`: a `react-pdf` `<Document>` that eagerly mounts **every page** of the PDF as a `<Page>` with both the text layer and annotation layer enabled (`PDFViewer.tsx:119-136`). There is no virtualization and no zoom control. "Scale" is not a scale at all — the page is sized by a width in CSS pixels, `Math.min(settings.pageWidth + 100, container.clientWidth - 48)` (`PDFViewer.tsx:38`), where `settings.pageWidth` is the *reading-column width slider* from the settings dropdown (`ReaderToolbar.tsx:208-216`). Changing text column width in book mode silently re-renders every PDF page at a new size.

`settings.mode === 'book'` renders `BookViewer`, which does **not** show the paper. It shows `paper.book_content.page_summaries[]` — LLM output. Each entry is produced by one OpenRouter call per page against the text sliced out by a `[Page N]` regex (`apps/api/.../papers/llm_service.py:113-129, 140-200`), asked to "Explain this page from a research paper" and return `{title, summary, key_concepts, has_math, has_figures}`. The `summary` markdown is rendered through `ReactMarkdown` + KaTeX + a lazily-imported Mermaid renderer. **There is no source text anywhere in book mode.** Only the first 5 pages are generated by default (`llm_service.py:317`); the rest show a dashed "not generated" card.

The **"SmartOutline"** is not an outline. `smart_outline` is built by iterating the generated page summaries and emitting one item per page with `title = ps["title"]` — an LLM-invented title — and `section_id = f"page-{ps['page']}"` (`papers/routes.py:198-207`, duplicated verbatim at `routes.py:284-293` and `llm_service.py:325-334`). A 40-page paper with 5 generated pages produces a 5-item "Contents" panel. The real structural outline type (`OutlineItem` with `block_id`) and its renderer `OutlinePanel.tsx` exist but are **never imported anywhere**.

**Book mode itself has two sub-modes** (`scroll` / `flip`) with their own header bar, page-dot navigator, and keyboard handler (`BookViewer.tsx:329-463`), stacked underneath the global toolbar.

## Data flow

**PDF selection → highlight anchor (trace the math):**

1. `PDFViewer.handleMouseUp` takes `range.getClientRects()` and stores `{x: rect.x, y: rect.y, w, h}` (`PDFViewer.tsx:60-65`). `getClientRects()` is **viewport-relative** — it already has scroll subtracted out.
2. `read/page.tsx:228-233` normalizes: `x / window.innerWidth`, `y / window.innerHeight`. This produces a **fraction of the browser viewport**.
3. That fraction is POSTed and persisted as `rects` on the highlight (`highlights/models.py`, `rects: Optional[List[dict]]`).
4. `PDFViewer.tsx:145-149` renders it as `left: ${rect.x*100}%` inside `<div className="relative">` that wraps the `<Page>` — i.e. **a fraction of the page element**.

Viewport fractions are read back as page fractions. These are different spaces by construction. A selection made on page 12 while scrolled halfway down the window records `y ≈ 0.4` and is drawn 40% down page 12's box. Change the window size, the sidebar collapse state, or the width slider, and every previously saved rect moves again. Nothing anywhere converts to PDF user-space (points), and `pdfjs`'s `viewport.convertToPdfPoint` is never called. `page_number` is the only surviving true provenance.

**Book selection → highlight anchor:** no geometry is captured at all. `handleBookTextSelect` stores `{selected_text, section_id: "page-N", page_number: pdfPage + 1}` (`read/page.tsx:212-217`). The `anchor: TextAnchor {exact, prefix, suffix, section_path}` field exists in both `types/index.ts:38-43` and the backend model — and is **never populated**. At render, `HighlightedText` re-finds the highlight by `text.indexOf(h.selected_text)` against each markdown string child (`BookViewer.tsx:89`).

**Explanations:** `HighlightPopup` → `createHighlight` → `openInlineExplanation(id, {x: rect.right, y: rect.bottom})` → `createExplanation` (`read/page.tsx:244-268`). The mutation is awaited synchronously; the LLM call happens inside the POST, so the request blocks until OpenRouter returns. Meanwhile the page polls `explanationsApi.list` every 2 s while the popup is open (`read/page.tsx:95`), refetching *all* explanations for the paper to see one new row.

**Persistence:** `readerStore` `partialize` keeps only `settings`, `sidebarCollapsed`, `minimapCollapsed` (`readerStore.ts:269-273`), and `resetReaderState()` fires on mount (`read/page.tsx:65-67`).

### Information architecture, honestly

Counting things that consume or occlude screen space in book mode: (1) `ReaderToolbar`, (2) left `SmartOutlinePanel` at 256 px, (3) `BookViewer`'s own mode-toggle header, (4) in flip mode an additional page-indicator bar **and** a bottom hint strip, (5) right `PDFMinimap` at 200–500 px, (6) floating `HighlightsPanel` bottom-left (200–400 px, up to 65 vh), (7) floating `HighlightPopup` (288 px), (8) floating `InlineExplanation` (450 × 520), (9) full-screen `FigureViewer` modal. That is **three horizontal bars stacked above the text and two resizable side rails plus three floating overlays**, all competing.

At 1280 px with both rails open, 556 px is chrome; the reading column's default `maxWidth` is 720 (`BookViewer.tsx:686`) — it fits with 4 px to spare, and stops fitting the moment the minimap is dragged to "L" (400 px). `HighlightsPanel` is `fixed bottom-4 left-4` (`HighlightsPanel.tsx:140`) so it sits **on top of** the outline sidebar. On an iPad in portrait (768 px) the layout has no breakpoint at all — `settings.minimapWidth` and `pageWidth` are absolute pixel values persisted to `localStorage` with no viewport awareness.

**Viewport coordinates persisted or held as state:** `settings.minimapWidth` and `settings.pageWidth` (persisted to `localStorage`, `readerStore.ts:269`); highlight `rects` normalized against `window.innerWidth/innerHeight` (persisted to **MongoDB**, `read/page.tsx:228-233`); `selectionPosition` and `inlineExplanation.position` (in-memory, `readerStore.ts:43, 51`).

**Touch hit targets:** `p-1` around `w-3 h-3` icons ≈ 20 px (`InlineExplanation.tsx:190-200`, `HighlightsPanel.tsx:342-351`); flip-mode page dots are `w-2 h-2` = 8 px (`BookViewer.tsx:389`). iOS minimum is 44 pt. `InlineExplanation` dismissal listens on `mousedown` only (`InlineExplanation.tsx:122`).

## What is worth keeping

- **`ReaderSettings` shape and the settings UI** (`readerStore.ts:8-19`, `ReaderToolbar.tsx:161-227`) — theme/font/line-height/width is the right vocabulary; only `pageWidth`'s double duty as PDF sizing needs unpicking.
- **The ask-mode taxonomy** (`types/index.ts:225-252`, `HighlightPopup.tsx:22-34`) — `explain_simply / explain_math / derive_steps / intuition / pseudocode / diagram` is a genuinely good product idea and the popup that surfaces it is well-shaped.
- **Highlight categories with colors** (`types/index.ts:375-402`) — keep, but collapse to one definition (three exist: `types/index.ts`, `types/highlight.ts`, `highlights/models.py`, and they disagree on `todo`/`review_later` and on the color of `question`).
- **Threaded explanations** (`Explanation.parent_id`, recursive `renderExplanation`, `InlineExplanation.tsx:171-284`) — the follow-up tree is a real differentiator; the data model supports it correctly.
- **The `TextAnchor {exact, prefix, suffix, section_path}` type** (`types/index.ts:38-43`) — already the right idea (W3C-style quote selector). It is simply never written. This is the single highest-leverage thing already in the repo.
- **`SourceLocation` / `BoundingBox` / `ContentBlock` types** (`types/index.ts:9-123`) — a proper block model with `id` and `source: {page, bbox, char_start, char_end}` is already declared. The reader ignores it entirely, but the vocabulary for document-space anchoring is written down.
- **`PDFMinimap`'s intent** — a source-of-truth thumbnail next to derived content is the right instinct for a "generated vs source" product, even though the implementation duplicates a whole `<Document>`.

## What should go

- `SearchResults.tsx` — references store fields that do not exist; would throw on mount. Delete or rebuild search from scratch.
- `ExplanationPanel.tsx`, `ExplanationModal.tsx` — superseded by `InlineExplanation.tsx`; zero importers; three copies of the same recursive renderer now exist.
- `OutlinePanel.tsx` — zero importers; the `block_id` outline it needs is never produced.
- `store/highlightStore.ts` + `hooks/useHighlights.ts` + `types/highlight.ts` — an entire parallel `book_id`-based highlight stack that no rendered component uses, plus the `highlightsApi.getBookHighlights/createHighlight/updateHighlight/explainHighlight/searchHighlights/exportHighlights` methods in `lib/api.ts:210-280` that serve only it.
- The viewport-normalization in `read/page.tsx:228-233` and the `%`-of-page overlay in `PDFViewer.tsx:145-154` — and every `rects` row already in the database, which is uninterpretable.
- `HighlightedText`'s `indexOf` re-anchoring (`BookViewer.tsx:72-148`).
- `.highlight-wrapper` / `.highlight-mark` CSS (`globals.css:49-148`).
- The triplicated `pdfjs.GlobalWorkerOptions.workerSrc` CDN assignment.
- The `smart_outline` construction duplicated across `routes.py:198`, `routes.py:284`, `llm_service.py:325`.
- `alert()` / `confirm()` at `read/page.tsx:148, 168, 287, 301`.

## Open questions

1. Is book mode meant to *replace* the paper or *annotate* it? Every architectural problem here (fake page citations, un-anchorable highlights, an outline made of model output) follows from the answer being "replace" while the UI implies "read".
2. `structured_content: StructuredContent` with `blocks[]` and `source.bbox` is declared on `PaperDetail` (`types/index.ts:202`) — is the backend actually producing it? Nothing in the reader consumes it. If it exists, real document-space anchoring is much closer than this audit assumes.
3. Should highlights be a single kind anchored in document space, or genuinely two kinds (source-anchored vs. generation-anchored)? Highlighting AI output is a legitimate feature — it just must not be citable as the paper.
4. What happens to the ~N existing highlight rows with viewport-fraction `rects`? Silent migration is impossible; they need to be marked degraded or dropped.
5. Is `FigureViewer` supposed to detect figures? It takes a `figureId` argument that `read/page.tsx:181-183` throws away and just opens a whole PDF page. Nothing crops to `ImageInfo.bbox`.
6. Is iPad a target for v1? If yes, the selection layer, hover-only affordances, hit targets, and eager full-document rendering are all pre-existing blockers, not polish.
